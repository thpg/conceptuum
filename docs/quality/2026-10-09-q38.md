## Names and views

A database schema description remains separate from a namespace. SQL schema
namespaces organize named objects, following the
[schema documentation](https://www.postgresql.org/docs/18/ddl-schemas.html).
Quoted and unquoted SQL identifiers are lexical forms. A schema-qualified
name has identifier components and is not a single identifier token. The
[lexical documentation](https://www.postgresql.org/docs/18/sql-syntax-lexical.html)
supports the distinctions without imposing one implementation's case-folding
policy on every SQL system.

The new query-defined view family contains ordinary nonmaterialized views
and materialized views. The [ordinary view](https://www.postgresql.org/docs/18/tutorial-views.html)
and its [stored definition](https://www.postgresql.org/docs/18/sql-createview.html)
are distinguished from result rows. A
[materialized view](https://www.postgresql.org/docs/18/rules-materializedviews.html)
persists query results that need not be current. Its
[refresh operation](https://www.postgresql.org/docs/18/sql-refreshmaterializedview.html)
has the view as its target. No automatic-refresh or guaranteed-speedup claim
is introduced, and no SQL schema is actually changed.

## Queries, plans, and algorithms

A retrieval query specification is an information object. SQL SELECT belongs
to both the statement family and this query-specification family. The
[SELECT documentation](https://www.postgresql.org/docs/18/sql-select.html)
supports separate result data and tabular result structure; duplicates are
not automatically excluded. A query is not automatically a network request.

Query plans reuse the existing plan concept, whose information-object genus
is also exposed in U3 without changing its home context. Plans contain plan
nodes. A node describes an operation; it is not the operation executing.
The [EXPLAIN documentation](https://www.postgresql.org/docs/18/using-explain.html)
supports these representations and scan distinctions.

Planning is an operation with a query description as input and a plan as
result. An optimizer is a software component with planning as its purpose.
The [planner description](https://www.postgresql.org/docs/18/planner-optimizer.html)
supports treating nested-loop, hash and merge joins as algorithms. The
existing nested-loop record is reused and retains its prior genus.
Algorithms have join execution as their purpose; no universally fastest
algorithm or optimal-plan guarantee is asserted.

Query execution remains distinct from planning and results. Only its
successful-completion restriction receives a result-producing relation,
consistent with the [executor model](https://www.postgresql.org/docs/18/executor.html).
Table scans target tables and index scans target indexes; neither is declared
mandatory for all queries. [Join execution](https://www.postgresql.org/docs/18/queries-table-expressions.html)
targets tabular inputs, separate from a chosen algorithm.

## Rules and column sets

Foreign-key and primary-key column sets are separate from the existing
integrity-constraint rules. One-column and multiple-column families combine
with key roles. The resulting intersections are connected to the corresponding
Q35 constraints. The [PostgreSQL constraint documentation](https://www.postgresql.org/docs/18/ddl-constraints.html)
supports primary and composite key-column meanings, while
[SQLite foreign-key documentation](https://www.sqlite.org/foreignkeys.html)
supports referencing-column distinctions. A foreign-key set is not required
to identify local rows uniquely, and a compound foreign key is not a single
column or a primary key by definition.

The old relational-algebra record moves from data to query language. Its
qualified meaning follows the
[Illinois Institute of Technology tutorial](https://www.cs.iit.edu/~cs561/cs425/algebra/home.html).
Its operators and tuple/set semantics still need a dedicated review; this
change does not equate SQL tables with mathematical sets.
