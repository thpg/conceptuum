## Repaired distinctions

The existing СУБД record 682 is reused as database-management software,
with genuine English DBMS terminology. It previously inherited database
data. Its deductive child is explicitly qualified as deductive DBMS software,
consistent with the old СУБД parent and implemented systems such as
[CORAL](https://research.cs.wisc.edu/coral/). The software is distinct from a
stored collection of facts and rules.

SQLite moves from database data to embedded relational DBMS and also receives
the existing software-library genus. The [SQLite description](https://www.sqlite.org/about.html)
supports its in-process library and database-engine meanings. A
client-server relational DBMS has both the relational DBMS and database-server
software genera. Embedded and client-server modes are not declared globally
disjoint: [SQLite can be used inside server applications](https://www.sqlite.org/whentouse.html)
without itself becoming a separate database-server process.

The database-table record moves from relational database to the existing
table data structure. The containing database receives a component relation
to database tables. A foreign key is qualified as an integrity constraint,
rather than a kind of database. SQL no longer has a database as an inherent
component. The database data collection's active storage capability is
rejected; a DBMS purpose and a database-management operation represent the
software/data distinction instead.

The old transaction record is qualified as execution of a database unit of
work and receives an operation genus. A separate structured record describes
a transaction. Commit, rollback, savepoints and rollback to a savepoint are
separate operations or information objects, following the
[PostgreSQL transaction explanation](https://www.postgresql.org/docs/18/tutorial-transactions.html).
No claim about every implementation's storage or isolation behavior is added.

Constraint kind and column count form independent axes. A composite foreign
key is both a foreign-key constraint and a multiple-column constraint;
a composite primary key uses the same arity family. A foreign key can refer
to its own table. CHECK, NOT NULL, UNIQUE and PRIMARY KEY remain distinct
declared constraint kinds. This follows the
[constraint documentation](https://www.postgresql.org/docs/18/ddl-constraints.html)
without importing universal NULL rules, mandatory primary keys, foreign-key
indexes or a requirement that the referenced key must always be primary.

Rows and columns are distinct from their table. The
[table documentation](https://www.postgresql.org/docs/18/ddl-basics.html)
supports this distinction; no fixed row order or unique-row guarantee is
encoded. A database schema definition and a table definition describe
structures rather than stored rows. This schema meaning follows the
[SQLite schema description](https://www.sqlite.org/schematab.html); SQL's
namespace sense is left for a separate record. Database-specific schema
matching refines the existing broader matching process.

A database index is an auxiliary data structure, separate from an integer
array index. Its querying purpose carries no guaranteed speedup, following
the [index introduction](https://www.postgresql.org/docs/18/indexes-intro.html).
There are 11 new non-genus relations linking purposes, targets,
components and an architectural style.
