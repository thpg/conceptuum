## Corrected homonym and dictionary boundaries

The physiological rest concept 253 incorrectly had API 299 as an attribute.
That U1 assertion is now rejected history. Both relaxation and mechanical
rest retain their existing meanings. REST receives a qualified IT label;
the ambiguous bare acronym is not added as a new alias.

[Fielding's definition of REST](https://ics.uci.edu/~fielding/pubs/dissertation/rest_arch_style.htm)
supports an architectural style, rather than a protocol or a synonym for
any JSON interface. Network APIs are narrowed separately by HTTP use and
REST-conforming design. RESTful HTTP API has both genera; the mapping is an
editorial intersection of those restrictions.

The dictionary's HTTP gloss requires TCP. [HTTP/3](https://www.rfc-editor.org/rfc/rfc9114.html)
provides the QUIC-based counterexample, so no universal TCP dependency is
imported. The dictionary's URL gloss is limited to web pages; the
[RFC 3986 URI/URL distinction](https://www.rfc-editor.org/rfc/rfc3986.html#section-1.1.3)
supports the broader locator meaning. URI has its own resource-identifier
family, separate from the existing programming-language identifier branch.

The method classes follow [HTTP semantics](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2):
safe methods belong to the idempotent family, while idempotence does not
require identical responses. Safety here is about requested semantics, not
security. GET and HEAD use the safe family; PUT and DELETE use the broader
idempotent family, as reflected in the [method reference](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Methods).
POST is left without either restriction; no blanket exclusion is introduced.
This describes the standard method meanings, not every individual endpoint's
implementation or configured behavior.

Request messages and method meanings remain separate. Message attributes,
software capabilities and purposes, and operation targets supply
14 non-genus relations. The software roles are qualified explicitly;
the old hardware client and server concepts are preserved. HTTP API does
not automatically imply REST conformance. URLs and protocols are different
kinds of information object.

No caching policy, automatic retry rule, protocol implementation, mandatory
transport or performance guarantee is introduced. Existing server/Jenkins classification, generic protocol/standard
links and software architecture descendants remain queued. The
[programming identifier definition](https://developer.mozilla.org/en-US/docs/Glossary/Identifier)
supports the qualified alias on the existing language-construct concept.
